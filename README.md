# Lifeathlete

Lifeathlete is a habit tracker with gamification, based on the "O Atleta da Vida" diagram
(10 life pillars: exercise, nutrition, nature, gratitude, screens, lightness, meditation,
active lifestyle, reading, family). It is an installable PWA in Portuguese and English.

Users check in their habits each day by tapping. They earn XP, levels and streaks, unlock
achievements, see a balance wheel of the 10 pillars, and have a dragonfly mascot. They can
share an image that contains no personal data. The product design (in Portuguese) is
`docs/superpowers/specs/2026-11-05-lifeathlete-design.md`. The implementation plan for
phases 1 to 3 is `docs/superpowers/plans/2026-11-05-lifeathlete-phases-1-3.md`.

## Architecture

```
Next.js 16 app (App Router, TypeScript, next-intl PT/EN, PWA)
  src/app/[locale]/...        pages: the public landing page (/{locale}), login, auth
                              callback / password reset, onboarding,
                              (app)/today, wheel, achievements, profile
  src/proxy.ts                session refresh, signed-out redirect, locale routing
  src/components/...          UI only (no business rules); landing/ is the front page
  src/lib/data/*.ts           typed data layer over supabase-js (getToday, logHabit, ...)
  src/lib/offline/queue.ts    IndexedDB queue for check-ins made offline
  public/sw.js                service worker (generated by scripts/build-pwa.mjs)
        │  supabase-js with the user's session
        ▼
Supabase
  Auth                        email + password, Google and Apple OAuth
  Postgres + RLS              supabase/migrations/0001..0011 (each user sees only own rows)
  Edge Functions              recalculate      rebuilds XP, level, streaks, pillar scores,
                                               achievements and mascot from habit_logs
                              weekly-summary   share card SVG for the caller
                              health-sync      daily steps from the Android app (Health Connect)
  supabase/functions/_shared/engine/   the pure gamification engine (XP, levels, streaks,
                                       achievements, wheel, mascot), unit-tested with Vitest
```

The client never writes `user_stats`, `pillar_scores` or `user_achievements`. RLS blocks
it. The client writes `habit_logs` (`source = 'manual'` only, in a small date window) and
its own `user_habits`, and then asks `recalculate` to recompute everything.

## Prerequisites

- Node.js 22 and npm
- The Supabase CLI (`npx supabase ...` works, the npm package downloads the binary) and
  Docker for a local stack (`supabase start`)
- PostgreSQL 16 binaries for `npm run test:db` (`/usr/lib/postgresql/16/bin`, or set
  `PGBIN`). Docker is not needed for this.
- Chromium for the Playwright e2e tests (`npx playwright install chromium`)

## Environment variables

Copy `.env.example` to `.env.local`. Every `.env*` file except `.env.example` is
git-ignored.

| Variable | Used by | Value |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | the Next.js app | API URL (local: `http://127.0.0.1:54321`) |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | the Next.js app | anon / publishable key |
| `NEXT_PUBLIC_SITE_URL` (optional) | the landing page metadata | public origin, e.g. `https://lifeathlete.example`. When set (or on Vercel, where `VERCEL_PROJECT_PRODUCTION_URL` is used), the landing page's Open Graph/Twitter URLs are absolute and include the share image `public/landing/og.png`. Without it, URLs stay relative and no share image is declared (Next would otherwise point it at `localhost`). |
| `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` | Edge Functions | provided by the Supabase Edge runtime, so you do not set them |

`npm run build` needs no variables, because every page that reads Supabase is rendered
dynamically. The `NEXT_PUBLIC_*` values are inlined at build time, so a production build
must be made with the real values set.

## Local setup

```bash
npm ci
npx supabase start            # starts the local stack and applies supabase/migrations
npx supabase status           # prints the API URL and anon key for .env.local
npm run dev                   # http://localhost:3000
```

`supabase/config.toml` is committed. It sets the project id `lifeathlete`,
`site_url = http://localhost:3000`, and the Auth redirect allow-list for
`/{pt,en}/auth/callback`. It turns off email confirmation (`[auth.email]
enable_confirmations = false`), which the e2e tests assume, and configures the
`recalculate`, `weekly-summary` and `health-sync` functions. The file was generated with
`supabase init` (CLI 2.122) and then edited. The CLI loads it without errors, but
`supabase start` itself was not run while writing this README, because Docker was not
available.

To re-apply all migrations to a fresh local database, run `npx supabase db reset`. The
catalog (pillars, habit templates, achievements) is seeded by migrations 0003 and 0004.
No `seed.sql` exists.

### Edge Functions

```bash
npx supabase functions serve                      # local, uses the running stack
npx supabase functions deploy recalculate weekly-summary health-sync --project-ref <ref>
```

The functions authenticate the caller from the `Authorization: Bearer <jwt>` header. The
app calls `recalculate` through `supabase.functions.invoke("recalculate")` after every
check-in and when Hoje opens with stats computed for an earlier day. The functions
import the engine from `supabase/functions/_shared/engine/`.

### OAuth providers (Google, Apple)

1. Create OAuth credentials with Google (Google Cloud console) and Apple (Sign in with
   Apple service id). Use the Supabase Auth callback as the authorised redirect URI:
   `https://<project-ref>.supabase.co/auth/v1/callback` in production, or
   `http://127.0.0.1:54321/auth/v1/callback` locally.
2. Locally, set `SUPABASE_AUTH_EXTERNAL_{GOOGLE,APPLE}_CLIENT_ID` and `..._SECRET` (for
   example in `supabase/.env`, which is git-ignored). Then set `enabled = true` under
   `[auth.external.google]` / `[auth.external.apple]` in `supabase/config.toml`. In a
   hosted project, enable the providers in the dashboard (Authentication > Providers).
3. Auth redirect allow-list: the app sends users back to `https://<your-domain>/pt/auth/callback`
   and `https://<your-domain>/en/auth/callback`. This covers OAuth, email confirmation and
   password reset (the reset link adds `?next=reset-password`, and the callback then opens
   `/{locale}/auth/reset-password`). Add both URLs, and the site URL, under Authentication >
   URL Configuration in a hosted project. Locally, `config.toml` already lists them for
   `localhost:3000` and `127.0.0.1:3000`.

Password reset uses the PKCE flow. The link in the email must be opened in the same
browser where the reset was requested.

## Recolha automática de dados

Value habits can be filled automatically, so the user does not type them. In Gerir hábitos,
"Preencher automaticamente" picks one metric per value habit (or "Não"); the data comes
from a connected source (Perfil > Integrações).

**Metrics** (the same keys in the database checks, the function contract and the client;
`AUTO_METRICS` / `METRIC_LIMITS` in `supabase/functions/health-sync/health-sync.ts`,
mirrored by `src/lib/health/metrics.ts` with a parity test):

| key | what | unit | accepted |
|---|---|---|---|
| `steps` | daily step total | steps | integer 0 to 100000 |
| `workout_minutes` | total duration of the day's workouts | minutes | integer 0 to 1440 |
| `sleep_hours` | sleep duration | hours | 0 to 24, rounded to 2 decimals |
| `mindful_minutes` | mindfulness / meditation duration | minutes | integer 0 to 1440 |

A value outside its range, NaN, negative or not a number is rejected, never clamped.
The habit's target should use the metric's unit.

**Database (migration `0012_health_metrics.sql`):**

- `user_habits.auto_source` holds a metric key (the old `'steps'` rows stay valid); only
  value habits can have one.
- `provider_connections.consented_categories text[]`: the metrics the user agreed to
  share. Server-side only (not in the client column grant), like `consented_at`,
  `consent_version` and `consent_withdrawn_at`. Rows that had accepted the steps-only text
  (`steps-2026-11-v2`) were backfilled to `{steps}`.
- `public.upsert_provider_activity(p_user_id, p_provider, p_rows jsonb) returns int`
  stores one provider's daily metrics (`[{ "date", "metrics": { key: number } }]`) in
  `provider_activity`. It validates again (provider `health_connect` or `huawei_health`,
  known keys, limits, real unique dates; anything else raises 22023 and writes nothing),
  and an existing day is **merged** (`payload || new`): syncing one metric never erases
  the others stored for that day.
- `public.fill_habits_from_activity(p_user_id, p_from, p_to) returns jsonb` fills, for
  at most 8 days, the user's active, non-archived value habits with a metric (at most 50
  per call, oldest first; the rest is `habitsIgnored`). Each value comes from the
  highest-priority provider that has that metric for that day, by the **source
  priority**: `health_connect`, `apple_health`, `huawei_health`, `fitbit`, `garmin`,
  `oura`, `strava` (a constant in the function). Other providers never fill a habit.
  `habit_logs.source` is the chosen provider. A manual log always prevails; an automatic
  one is replaced by a higher-priority or newer value. It returns `{ written,
  skippedManual, habitsUpdated, habitsIgnored }` and is idempotent.
- Both functions are `security definer` and can be executed by `service_role` only.
- `public.apply_health_logs` (0011) is kept unchanged, because the deployed health-sync v1
  calls it until v2 is deployed. A later cleanup migration may drop it.

**Edge Function `health-sync` v2** (`supabase/functions/health-sync/`, `verify_jwt =
true`). The user comes only from the `Authorization: Bearer` JWT. Every `POST` body has
`source: "health_connect"` (any other source gets `unsupported_source`):

- `{ action: "connect", consent: true, consentVersion, categories: [metric, ...] }`:
  `consentVersion` must be the current text (`CURRENT_CONSENT_VERSION =
  "metrics-2026-11-v3"`, mirrored by `HEALTH_CONSENT_VERSION` in
  `src/lib/data/integrations.ts`; bump both when the text changes, and every user is
  asked again). `categories` must be non-empty, unique and known. It stores the categories
  (replacing the old ones), the version and the time, and clears a withdrawal. The response
  is `{ ok, status: "connected", categories }`.
- `{ action: "sync", days: [{ date: "YYYY-MM-DD", metrics: { steps?, workout_minutes?,
  sleep_hours?, mindful_minutes? } }] }`: 1 to 7 unique dates within the last 7 local days
  (profile timezone). Each day needs at least one metric and no unknown key. The
  **legacy** phase 1 day `{ date, steps }` is still accepted as `metrics: { steps }`. The
  connection must be connected, with consent to the current version that covers **every
  metric sent**. Otherwise the answer is 403 `consent_required` and nothing is written, so
  an unconsented category is never stored. The function then calls
  `upsert_provider_activity` and `fill_habits_from_activity` for the request's date range,
  updates `last_synced_at` and asks `recalculate` for fresh stats (at most once a minute).
  The response is `200 { ok, status, lastSyncedAt, days, metricsReceived, habitsUpdated,
  skippedManual, habitsIgnored }`. All v1 field names are kept, and `metricsReceived`
  (the metric keys received) is new.
- `{ action: "status" }`: `{ ok, status: "connected" | "disconnected" | "none",
  categories, consentCurrent, lastSyncedAt }`, read with the service role. The screen
  uses it after a reload, because the client cannot read the consent columns. A
  connection that accepted an older text is `consentCurrent: false`, and the screen asks
  for consent again.
- `{ action: "disconnect" }`: stops collection and records the withdrawal. The imported
  history and the record of what was accepted are kept.
- Errors are codes only: `unauthorized` (401), `invalid_request` (400),
  `unsupported_source` (400), `consent_required` (403), `sync_failed` (500). The pure
  logic is `health-sync.ts` (unit-tested). `index.ts` is thin I/O glue.

**Web:** Integrações (`/{locale}/profile/integrations`) shows one checkbox per category
(all unchecked; at least one is needed to continue), each with what is read, and the
consent text. It also has connect, "Sincronizar agora" and "Desligar". The connected
state lists the consented categories. The native bridge (`src/lib/health/bridge.ts`:
`isAvailable`, `requestPermission(categories)` resolving to the granted subset, and
`readMetrics(days, categories)`) is null in the browser and the PWA, so there the screen
only explains that collection needs the Android app. The sync flow drops invalid,
unconsented or out-of-window values before sending. Hoje shows "via Health Connect" or
"via Huawei Saúde" on filled habits.

**Consent.** Before connecting, the user picks the categories and accepts a text that
says: only the selected categories are read, as daily totals or durations; each sync
sends the last 7 days; the values are stored even before a habit uses them; they are
kept while the account exists, including after disconnecting; they are not verified;
they fill the habits the user chooses; and how to disconnect (the imported history is
kept). There is no way yet to delete imported data (no client delete, no account
deletion).

**Limitation.** The values are sent by the user's phone (or, later, a provider cloud)
and **cannot be verified** by the server. A modified client can send any number within
the limits above. This is the same trust level as a manual log, which is self-reported
too.

**Not built yet:** the native Android shell (a Capacitor plugin over Health Connect that
registers a `HealthBridge`), the Huawei Health Kit cloud adapter (which will write
`huawei_health` rows through `upsert_provider_activity`), and Apple Health (not
supported: the function answers `unsupported_source`). Nothing is published to an app
store.

**Deploy order:** apply migration 0012 first, then deploy the new function (`npx supabase
functions deploy health-sync --project-ref <ref>`). Health-sync v1 keeps working during the
switch: it still calls `apply_health_logs` and writes `provider_activity` itself, and
0012 keeps both valid. After v2 is live, every user connected with the steps-only consent
is asked to consent again.

## Landing page

`/{pt,en}` is the public front page (`src/app/[locale]/page.tsx`, components in
`src/components/landing/`, copy in the `landing` message namespace). It is statically
rendered (no cookies, headers or Supabase), has no client code of its own and is pure
SVG/CSS apart from two app screenshots. Both "Entrar" links go to `/{locale}/login`, which
already sends signed-in users on to Today. Its colors are tokens (`--landing-*` in
`src/styles/tokens.css`); `src/styles/contrast.test.ts` checks every text color against
each landing surface and gradient stop in both themes.

- The app screens `public/landing/{today,wheel}-{pt,en}.webp` are real screens (dark
  theme, sample data, 390x844 at 2x). They were captured from the real `TodayView` and
  `WheelView` with a temporary preview page that is not committed.
- `node scripts/generate-og-image.mjs` renders the share image `public/landing/og.png`
  (1200x630) with Playwright's Chromium. Run it when the hero changes.

## PWA

- `npm run build:pwa` (also run automatically as `prebuild`) generates `public/sw.js` and
  the localized offline pages `public/offline/{pt,en}.html` from their sources. A unit test
  fails if the committed files drift from those sources.
- `node scripts/generate-icons.mjs` renders the dragonfly icons in `public/icons/` with
  Playwright's Chromium. Run it only when the mark changes.
- The manifest `start_url` is `/?source=pwa` (its `id` stays `/`). `/` itself is the
  landing page, so the proxy redirects exactly `/?source=pwa` to `/{locale}/today` (the
  `NEXT_LOCALE` cookie, then `Accept-Language`, then `pt`); the guards then send signed-out
  users to login. A plain `/` still goes to the localized landing page.
- Offline, the worker serves the stored Hoje for the launch URL `/?source=pwa` only. The
  landing page (`/`, `/pt`, `/en`) is never stored, so offline it gets the localized
  offline page like any other uncached page.
- The service worker caches static assets. For offline use it stores only the Hoje page
  (responses marked by the proxy, kept for at most 24 hours, and only HTTP 200). It never
  caches auth, login, onboarding or Supabase requests. Signing out clears the stored pages.

## Deployment

1. Create a Supabase project. Then run `npx supabase link --project-ref <ref>` and
   `npx supabase db push` to apply `supabase/migrations`.
2. Deploy the functions (see above), configure the Auth URLs and the providers.
3. Deploy the Next.js app (for example on Vercel), with `NEXT_PUBLIC_SUPABASE_URL` and
   `NEXT_PUBLIC_SUPABASE_ANON_KEY` set for the build.
4. Apply new migrations before deploying an app version that reads their columns
   (`habit_logs.target`, `user_habits.pauses`, `user_stats.computed_for`), and apply 0012
   before deploying health-sync v2 (see "Recolha automática de dados").

None of these deployment steps were run against a real Supabase project while writing
this README.

## Known limitations

- **Users can inflate their own XP.** Lifetime columns of `user_habits` (`created_at`,
  `deleted_at`, `target`, `kind`, `pauses`) and the target stored on each log can be
  written by the client, and the engine trusts them. No leaderboard or other social
  comparison exists, so this affects only the user's own numbers. Migration 0009 closes
  one gap: manual logs are only accepted for dates from (local today − 3) to (local
  today + 1). The other gaps (column grants or triggers on the lifetime columns) are not
  done.
- **Shared devices.** If a user never signs out, the stored offline Hoje page (at most
  24 hours old) stays in that browser profile and can be seen offline by the next person.
  The per-user offline check-in queue in IndexedDB is not cleared on sign-out. Its items
  are only sent for the same account.
- The Roda screen does not have the weekly and monthly history from the spec yet.
- Medal progress bars are shown only for global-streak achievements. Other achievements
  show locked or unlocked.
- Provider integrations (Strava, Fitbit, Garmin, Oura, Huawei) and the native app (phase 6)
  are not built.
- The e2e specs were written and type-checked, but they were never run against a live
  Supabase stack in the original implementation environment (no Docker there). The Edge
  Functions' Deno adapters were never executed there either. Their logic is covered by
  Vitest through runtime-agnostic modules.
